# Server SDK publishers

Minimal LiveKit server RTC SDK publisher programs used by
`OpenViduTestAppE2eServerSdkTest`, one per SDK:

| Directory           | SDK                                       | Video source            |
| ------------------- | ----------------------------------------- | ----------------------- |
| `go-publisher/`     | `github.com/livekit/server-sdk-go/v2`     | pre-encoded files       |
| `node-publisher/`   | `@livekit/rtc-node`                       | synthetic frames (FFI)  |
| `python-publisher/` | `livekit` (Python `rtc`)                  | synthetic frames (FFI)  |
| `rust-publisher/`   | `livekit` crate                           | synthetic frames (FFI)  |
| `dotnet-publisher/` | `Livekit.Rtc.Dotnet`                      | synthetic frames (FFI)  |

Each program is launched by `OpenViduTestE2e#startServerSdkPublisher` inside a
plain runtime container of its language (see that method for the images and run
commands). The directory is mounted read-only at `/app`, copied to `/work` and
run there. The dependency cache at `/cache` is a Docker volume that lives only
for the test JVM that created it (one per SDK, removed with the containers when
the JVM ends), so a run never sees the downloads, builds or caches of a previous
run or of another job on the same machine; within a run the publishers of an SDK
share it, which keeps the Rust publisher's libwebrtc build to one per run. The
program must print the exact line
`TRACK_PUBLISHED` once the track is published: the Java test waits for it before
asserting, and stops the container when the test ends, so the programs never
exit on their own.

## Behaviour

Every publisher joins the room of `LIVEKIT_TOKEN` with dynacast disabled and
publishes a single video track with codec `VIDEO_CODEC` (`vp8`, `h264`, `vp9`
or `av1`) and `VIDEO_LAYERS` layers (`1`, `2` or `3`):

- `VIDEO_LAYERS=1` (default): one plain RTP encoding. No simulcast for
  VP8/H264, no SVC (scalability mode `L1T1`) for VP9/AV1.
- `VIDEO_LAYERS=2` and `3`: simulcast for VP8/H264 and SVC `L2T2` / `L3T3` for
  VP9/AV1.

### FFI-based SDKs (node, python, rust, dotnet)

They encode raw frames themselves and push synthetic animated frames forever.
The frames are textured and moving (per-pixel gradients shifted every frame),
not flat colours: a flat frame compresses to a few hundred bytes, so the
simulcast / SVC layers ran at about 10 kbps with one RTP packet per frame, and
under CPU load (fewer frames per second) the SFU's stream tracker declared the
upper layers gone for lack of packets, leaving subscribers on the lowest layer.
Textured frames give every layer a realistic bitrate and steady packet flow.
The source is 640x480 for one or two layers and 1280x720 for three layers,
because the SDKs only split a simulcast source in three layers from 960 px
wide. The SDKs derive the simulcast layers from the source: 480x360 + 640x480
from the 640x480 source (4:3 presets) and 320x180 + 640x360 + 1280x720 from the
1280x720 one (16:9 presets).

They publish with degradation preference `MAINTAIN_RESOLUTION`. The SDKs'
default for camera tracks is `MAINTAIN_FRAMERATE`, which lets libwebrtc scale
the source down under CPU overuse or bitrate pressure (1280x720 becomes
960x540, and every layer shrinks with it): the Java test identifies each layer
by its declared frame width, so on a loaded machine (GitHub-hosted runners) the
expected widths were never observed. With `MAINTAIN_RESOLUTION` libwebrtc drops
frames instead and the layer sizes stay as declared. They also capture at 15 fps
with several layers, because three software encoders at 30 fps trigger that
adaptation even faster.

### Go SDK

The Go SDK forwards pre-encoded samples and has no encoder. The publisher loops
forever the files generated by the Java test with the host's `ffmpeg` (Annex-B
for H264, IVF for VP8/VP9/AV1), one file per layer:

- `VIDEO_LAYERS=1`: one plain RTP encoding from `VIDEO_FILE` (640x480). This is
  the publish shape of every Go SDK client (`lk` CLI, `lk load-test`, Go
  agents): the `AddTrackRequest` declares no codec, the exact configuration that
  triggered the mediasoup Producer codec-binding bug.
- `VIDEO_LAYERS=2`: two RID simulcast layers (LOW 320x240, HIGH 640x480) from
  `VIDEO_FILE_LOW` / `VIDEO_FILE_HIGH`.
- `VIDEO_LAYERS=3`: three RID simulcast layers (LOW 320x180, MEDIUM 640x360,
  HIGH 1280x720) from `VIDEO_FILE_LOW` / `VIDEO_FILE_MEDIUM` /
  `VIDEO_FILE_HIGH`.

Because it cannot produce SVC streams, its VP9/AV1 multi-layer cases are
skipped by the Java test (RID simulcast of SVC-class codecs is not a supported
publish shape). The layer sizes in `go-publisher/main.go` must match the files
generated by `startServerSdkPublisher`.

## Environment variables

| Variable       | Publishers | Meaning                                                    |
| -------------- | ---------- | ---------------------------------------------------------- |
| `LIVEKIT_URL`  | all        | LiveKit server URL                                         |
| `LIVEKIT_TOKEN`| all        | Ready-made join token (identity `<sdk>-publisher`)         |
| `VIDEO_CODEC`  | all        | `vp8`, `h264`, `vp9` or `av1`                              |
| `VIDEO_LAYERS` | all        | `1` (default), `2` or `3`                                  |
| `VIDEO_FILE`   | go         | Pre-encoded 640x480 file for one layer                     |
| `VIDEO_FILE_LOW`, `VIDEO_FILE_MEDIUM`, `VIDEO_FILE_HIGH` | go | Pre-encoded file per simulcast layer |

The token is generated by the Java test so the programs stay short (no per-SDK
token dependency) and work with any API secret length.

# Android app

`android-app/` is a minimal native Android app built with the official LiveKit
Android SDK (`io.livekit:livekit-android`), used by `OpenViduAndroidE2eTest`. Its
only activity (`MainActivity.kt`) joins a Room with the URL and token typed into
it, publishes the camera and the microphone, and shows the local and remote
videos. The test drives it with Appium (UiAutomator2), as the browser tests drive
the testapp with Selenium: `OpenViduAndroidAppUser` types into it, taps its
buttons and switches, and reads the JSON that the app writes in its `status`
view twice a second:

- the Room state, the number of each Room event received, the data messages
  received, and the connection quality and speaking state of every participant;
- for each local track, what the camera or the microphone captures, and for the
  camera the outbound layers of its encoder from the WebRTC stats (one per
  simulcast layer, or one with SVC: active or paused, codec, scalability mode,
  encoder, size, frames);
- for each remote track, what reaches the app (a `VideoSink` / `AudioTrackSink`
  per track: frames and last frame size, or samples and level), its stream state,
  and for video its inbound-rtp WebRTC stats (codec, decoder, SSRC, packets,
  frames decoded, frame size, key frames, PLIs, NACKs).

Its controls: the video codec (`vp8` by default, `vp9` and `av1` with SVC) and
simulcast, applied when connecting; "Test tone" (see below); "Camera" and "Mic"
(mute and unmute); "Send data" (a reliable data message on topic
`openvidu-e2e`); and "Large videos" and "Show videos", which resize and hide the
remote video views. The Room uses adaptive stream and dynacast, as LiveKit
recommends for apps, so those two decide the layer each remote video is received
at, and whether it is received at all.

Things the app does because it runs in an emulator, each explained in the code:

- **Test tone**: the emulator gets no host audio (QEMU's null driver, see the
  image), so its microphone records silence. The switch mixes a 440 Hz tone into
  the microphone track through the SDK's `MixerAudioBufferCallback`, as the fake
  microphone of a browser produces one, and in beeps (400 ms on, 200 ms off) as
  Chrome's does: WebRTC's noise suppression learns a steady tone as background
  noise and attenuates it, until the server stops hearing the app as an active
  speaker. A PulseAudio sine wave as the emulator's microphone was tried first and
  did not work reliably: whenever an app recorded, the guest's audio HAL failed
  most reads or got zeros.
- **Software video decoding** (`LiveKitOverrides.videoDecoderFactory`), on an
  emulator only: its "hardware" decoders (`c2.goldfish.*`) hand every frame to the
  host and fall behind, and the camera, whose frames come from the host as well,
  then gave 1 frame per second.
- **No layout pass while the status changes**: the status view has a fixed height
  and the state view is only set when it changes. The SDK's adaptive stream
  recalculates the visibility of a video view 2 s after the last layout pass of
  the window, so a status that laid the window out every 500 ms kept every
  remote video paused.

Even so, the emulated camera gives about 11 frames per second, and fewer while
the app also decodes and renders remote videos, so the tests require the videos
the app sends and receives to keep playing at 1 frame per second or more
(`ANDROID_MIN_VIDEO_FPS`), not at the browsers' rate: they check that video and
audio flow and play in both directions, not their quality.

The tests judge the video the app receives by the frames WebRTC decodes (its
inbound-rtp stats, as for the browsers), not by the frames that reach the app's
own `VideoSink`, which the status shows as well. With adaptive stream, the SDK
makes WebRTC stop and recreate the receive stream of a video every time it stops
receiving it and back (`VideoTrack.setShouldReceive`, called from a coroutine of
its IO dispatcher while that native call belongs to the signaling thread), and in
about 4 of 10 runs, on both RTC engines, the recreated stream decodes frames that
reach no sink (logcat: `VideoReceiveStreamInterface not connected to a
VideoSink`): a problem of the LiveKit Android SDK (2.30.0), not of the server.
The tests log a warning when they see it.

Versions: Gradle 9.9.0 (wrapper, with the distribution checksum), Android Gradle
plugin 9.5.1 (which compiles Kotlin itself), LiveKit Android SDK 2.30.0, and
`compileSdk` / `targetSdk` 36, the API level of the emulator image. The SDK
depends on `com.github.davidliu:audioswitch`, which only JitPack publishes, so
`settings.gradle.kts` adds JitPack for that group alone.

Dependabot (`.github/dependabot.yml`, multi-ecosystem group
`android-test-environment`) opens one weekly pull request with every update of
this test environment:

- `gradle`: the Gradle wrapper (with its checksum), the Android Gradle plugin and
  the libraries of `app/build.gradle.kts`;
- `docker`: the base images of `docker/openvidu-test-e2e-android` (Ubuntu, LTS
  releases only, and the Node.js image Appium's runtime is copied from);
- `npm`: Appium and its UiAutomator2 driver, which the image installs with
  `npm ci` from its `appium/package.json` and `package-lock.json`;
- `maven`: the Appium Java client of `openvidu-test-browsers`.

Before merging, run the tests on the pull request's branch with the CI workflow
below, building the image when the pull request changes it, and push the image
(`create_image.sh`) once merged. Dependabot cannot see the Android SDK packages of
the image, which are bumped by hand: its `CMDLINE_TOOLS` argument, and its `API`
argument, which sets the platform, build tools and system image (a new API level
also means `compileSdk` / `targetSdk` here and a new image tag, the Android
version: `16` for API 36, in `create_image.sh` and `OpenViduTestE2e#ANDROID_IMAGE`).
The emulator and the platform tools are the latest at each build of the image.

How the tests run it, all in the image `openvidu/openvidu-test-e2e-android`
(`docker/openvidu-test-e2e-android`, which carries the JDK and the Android SDK
platform as well as the emulator and Appium):

1. `OpenViduTestE2e#prepareAndroidApp` builds the debug APK once per JVM, in a
   one-shot container of the image, the same way as the server SDK publishers:
   the directory is mounted read-only at `/app` and built in `/work`, and the
   JVM's `android` cache volume holds Gradle's downloads (`/cache/gradle`) and
   the APK (`/cache/android-app/app-debug.apk`). From an empty cache the build
   takes 2 to 5 minutes.
2. `OpenViduTestE2e#setupAndroidApp` boots one emulator for all the tests: it
   starts its container (host network, `/dev/kvm`, the cache volume read-only),
   waits for the image's health check (booted, animations off, Appium answering
   on `:4723`; about a minute) and installs the APK with every permission
   granted (`adb install -r -g`). Every test then opens an Appium session on the
   app. When an earlier test used the emulator, it first kills the app's
   process, turns the network back on (the reconnection test turns it off) and
   clears the logcat, so each test starts with a fresh app. After a failed test
   the next one boots a new emulator, and the last test stops it. The tests are
   skipped on a host without KVM: there the emulator would need tens of minutes
   to boot.
3. Inside the emulator `localhost` is the emulator itself and the host's
   loopback is `10.0.2.2`, so `livekitUrlForAndroidEmulator()` rewrites a
   `localhost` `LIVEKIT_URL` to that address (hence `usesCleartextTraffic` in
   the manifest for `ws://`). The media goes through the emulator's NAT to the
   candidates the server advertises.

In CI they run on their own, in openvidu-pro's workflow "OpenVidu Pro E2E Android
tests" (`.github/workflows/openvidu-pro-e2e-android-tests.yml`, dispatched by
hand), on the self-hosted runners: EC2 instances have no KVM unless launched with
options its runner action does not pass. It fails at once on a runner without
`/dev/kvm` and when any test was skipped, so a run cannot pass without testing,
and it pulls the image while the job builds, or builds it from the checkout of
`ref-openvidu` with `build-android-image` (tagged `:test` and passed to the tests
as `-DANDROID_IMAGE`).

To build it on a developer machine, run `./gradlew assembleDebug` with a JDK 17
or newer and `ANDROID_HOME` pointing to an Android SDK with platform 36, or
open the directory in Android Studio.
